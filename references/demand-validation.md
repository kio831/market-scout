# Demand Validation — 需求验证（v2.0 新增，流水线第 2 阶段 VALIDATE）

本文件定义"一个市场机会是否存在**真实、足够强、可能付费**的需求"的验证方法。它是 Find → Validate → Evaluate → Monetize 流水线的第二阶段，**复用而非替换** v1.1 的 Problem Card、三类搜索、证据链与证据等级，只新增"需求强度判定、目标用户分层、付费理由链"三层结构化判断。产出为 `templates/demand-validation-card.md`。

> 阶段定位：**FIND（发现问题/机会）→ 【VALIDATE（本文件）】→ EVALUATE（项目评估）→ BLUEPRINT（机会转项目）→ MONETIZE（商业化与获客）**。
> 流水线编排、阶段间数据契约、调用失败降级见 `references/pipeline-and-runtime.md`。

## 0. 与 v1.1 已有能力的复用关系（禁止重复造轮子）

| 本阶段需要的判断 | 直接复用的 v1.1 能力 | 本文件新增 |
|---|---|---|
| 用户是否真的遇到问题 | Problem Search、Problem Card、证据等级 A/B/C（`problem-framework.md`、`market-research.md`） | 需求强度 6 信号合成 |
| 用户现在怎么解决 | Solution Search（`market-research.md` §0.2） | 替代方案成本量化表 |
| 是否有人付钱 | Payment Search、付费信号分级（`payment-validation.md` §1-2） | 付费理由链（JTBD） |
| 结论是否可信 | Evidence Chain 五段式、7 项属性、置信度（`evidence-chain.md`） | 需求证据可信度矩阵 |
| 用户画像 | Problem Card"用户"字段 | 核心/扩展/非用户三层分层 |

**铁律**：进入本阶段前，FIND 阶段至少已有 Problem Card 与 Problem Evidence；没有 Problem Evidence 的"机会"不进入验证，直接退回 FIND 或按停止机制处理（`payment-validation.md` §6）。

## 1. Demand Validation 必须回答的 6 个问题

1. **用户痛点（Pain Points）**：具体痛在哪？是哪一类（`problem-framework.md` §2 十分类）？不解决的后果能否量化（时间/钱/风险/情绪）？
2. **目标用户（Target Users）**：谁最痛？分核心用户、扩展用户、非用户三层（§3），禁止写"所有人/中小企业"这种无法触达的画像。
3. **需求强度（Demand Strength）**：痛到什么程度、多频繁、是否主动找方案（§2 合成 1-10 分，分必须绑定证据）。
4. **当前解决方案（Current Alternatives）**：不用你的方案时，用户现在用什么解决？花了多少时间/钱？为什么不满意（§4）？
5. **为什么愿意付费（Willingness-to-Pay Reasoning）**：用户"雇佣"这个方案完成什么任务？现在为替代方案付了多少？切换/购买理由是什么（§5 付费理由链）？
6. **需求证据与可信度（Evidence & Confidence）**：每个结论的证据等级（A/B/C）、置信度（高/中/低）、缺口是什么（§6）。

## 2. 需求强度模型（Demand Strength，1-10，分绑定证据）

需求强度由 6 个可观察信号合成，**每个信号都必须有证据或显式标注【无直接证据，推断/假设】**，禁止凭"我觉得需求很大"打分。

| 信号 | 含义 | 强（对应高分）的可观察表现 |
|---|---|---|
| S1 痛点严重度 | 不解决的损失大小 | 直接亏钱/合规风险/每天被折磨 > 只是"不方便" |
| S2 发生频率 | 多久遇到一次 | 每天 > 每周 > 每月 > 一次性（复用 Problem Card"频率"） |
| S3 主动寻找 | 用户是否主动找方案 | 主动搜索、发求助帖、询价、加群问、对比工具 |
| S4 现有预算 | 是否已经在为替代方案花钱 | 已买工具/已外包/已雇人 > 只用免费方案硬扛 |
| S5 不满程度 | 对现有方案是否明确不满 | 公开吐槽现有工具贵/难用/易错 > 默默忍受 |
| S6 增长趋势 | 需求是否在变多 | 相关讨论/岗位/服务数量随时间上升（需两个时点证据） |

**合成规则**：
- 6 信号各按 0-10 给分（同样要求"分数+理由+证据+不确定性"四要素，沿用 `problem-framework.md` §4）。
- Demand Strength = 6 信号均分，四舍五入到 0.1；**S1/S2/S3 任一 ≤ 3 时，Demand Strength 上限 5**（不够痛/不频繁/不主动找的需求，强不到哪里去）。
- S4（现有预算）是付费的前置信号，但不等同于"会为你的方案付费"——后者属于付费理由链（§5）与 Payment 证据。

### 需求强度分档（输出结论用）

| 分数 | 结论标签 | 含义 |
|---|---|---|
| 8-10 | **强需求 Strong Demand** | 高频、很痛、主动找、已有预算；优先推进 EVALUATE |
| 5-7 | **中等需求 Moderate Demand** | 部分信号强、部分缺证据；可推进但必须在结论里点名最弱信号与补证据动作 |
| 1-4 | **弱需求 Weak Demand** | 偶发/不痛/不主动找/无预算；原则上不推进，按停止机制输出或退回 FIND 收窄问题 |

## 3. 目标用户三层分层（禁止"所有人"）

| 层级 | 定义 | 必须写清 |
|---|---|---|
| **核心用户 Core Users** | 痛得最深、频率最高、最可能最先付钱的一小群人 | 具体画像 + 具体场景 + 数量级估计（标注观察/推断/假设）+ 在哪里能触达 |
| **扩展用户 Adjacent Users** | 有同样问题但痛得轻/频率低，或相邻场景的人 | 与核心用户的差异、后续扩展顺序 |
| **非用户 Non-users** | 看似相关但不会付费/无法触达/已有满意方案的人 | 明确排除，避免后期把资源花在错的人身上 |

**判定问题**：如果只能服务 10 个人，是哪 10 个？答不出具体画像 = 用户分层未完成，不得进入 EVALUATE。

## 4. 当前解决方案与替代成本（复用 Solution Search）

用 Solution Search（`market-research.md` §0.2）找全用户"不用你时"的所有替代路径，并量化替代成本：

| 替代方式 | 用户现在怎么做 | 时间成本 | 金钱成本 | 技能/学习门槛 | 明确不满点 |
|---|---|---|---|---|---|
| 纯人工硬扛 |  |  |  |  |  |
| 免费/通用工具（Excel/通用 AI 等） |  |  |  |  |  |
| 付费工具/SaaS |  |  |  |  |  |
| 外包/人工服务 |  |  |  |  |  |
| 干脆不做（忍受损失） |  |  |  |  |  |

**关键结论**：
- "用户真正购买的是什么"（结果/时间/效率/成本降低/任务完成/信息/质量，沿用 `market-research.md` §4）。
- **替代成本就是后续定价的价格锚**（传递给 MONETIZE 阶段，见 `monetization-gtm.md`）。
- 如果所有替代方案都让用户"成熟且满意"，触发停止机制（`payment-validation.md` §6）。

## 5. 付费理由链（Willingness-to-Pay / JTBD Chain）

按顺序回答 5 环，前一环无证据就不得跳到"愿意付费"结论（防跳级规则同 `evidence-chain.md`）：

```
① Job to be Done：用户要"雇佣"产品完成什么具体任务？（要结果，不要功能）
        ↓
② Current Cost：现在完成这个任务付出多少时间/钱/情绪成本？（来自 §4，有证据）
        ↓
③ Switch Trigger：什么事件会逼他现在就解决（报销日/上新季/被罚款/老板催/离职交接）？
        ↓
④ Pay Reason：为什么愿意为"你的方案"而不是继续用替代方案付钱？（更便宜/更快/更省心/只有你能做/降低风险）
        ↓
⑤ Pay Ability & Authority：他有没有预算、能不能自己拍板付钱？（员工想用但老板不批 = 有需求无付费权）
```

**判定**：
- 5 环全部有证据支撑 → 付费理由成立，传递给 EVALUATE（计入 Market Potential）与 MONETIZE（定价/Offer 设计）。
- 只有 ①②、缺 ③④⑤ → 写【付费意愿未验证】，只能作为假设；这正是后续"不开发产品的验证方式"要解决的（`monetization-gtm.md`）。
- ⑤ 不成立（使用者≠付费者且无拍产权）是高频致命问题，必须在卡片里显式红旗标注。

## 6. 需求证据可信度矩阵（复用证据链）

本阶段每个结论标注两维可信度（沿用 `evidence-chain.md` 的证据类型与置信度口径）：

| 结论类型 | 最低证据要求 | 达不到时 |
|---|---|---|
| 痛点真实存在 | ≥2 个独立一手来源（原文/访谈/观察） | 标 C，结论写"假设" |
| 需求重复发生 | 多个独立来源重复提到同类问题 | 单一个案不得判重复需求 |
| 用户主动找方案 | 求助帖/搜索/询价/对比行为证据 | 无则 S3 记低分 |
| 已有替代预算 | 在售服务/公开价格/成交/已购买证据 | 无则 S4 记低分，且 Payment 不得高估 |
| 愿为"本方案"付费 | 针对本方案的询价/报价/预付/成交 | 只有"听起来不错"不算，最多 CUSTOMER_FOUND（见状态机） |

**需求验证结论（三选一，必须显式输出）**：
- ✅ **真实需求已验证 Validated**：痛点+频率+主动寻找有 A/B 级证据，付费理由链至少通到 ④。
- 🟡 **需求存在但付费未验证 Unvalidated Payment**：需求证据够、付费证据缺（最常见，允许进入 EVALUATE，但 EVALUATE 结论通常只能是"建议验证后再做"）。
- ❌ **伪需求/弱需求信号 Weak or False Signal**：热度高但无人主动找、无人花钱、替代方案已让人满意，或只有单一案例——不推进，说明原因与重启条件。

## 7. 输出要求（Demand Validation Card）

- 使用 `templates/demand-validation-card.md`，六个问题逐项回答，全部结论可追溯到 Evidence Card。
- 给出 Demand Strength 分数与分档、三层用户、替代成本表、付费理由链 5 环、需求验证结论。
- 输出"要把结论从当前水平再推进一步，唯一要补的证据是什么"（只做一件事，与状态机瓶颈推进原则一致，`opportunity-state-machine.md` §4）。
- 双语与排版规范见 `SKILL.md` §输出与双语规范；阶段失败/无搜索能力时的降级见 `pipeline-and-runtime.md` §3。
