# Payment Validation — 付费验证与第一笔钱（v1.1）

本文件定义付费信号识别、**付费评分分档**、**第一笔钱执行清单**、定价与交付、验证指标与**停止机制（含重启条件）**。用于 Payment / Business Validation、First Customer Validation 与 Execution Mode。

## 1. 付费信号识别

判断"这个需求是否已经有人愿意付钱"。从强到弱：

**强信号（A 级证据）**：
- 已有在售服务/产品并有人购买（代做店铺、SaaS 订阅、付费课程、咨询收费）。
- 用户在评论区/帖子中明确"我愿意付钱""多少钱都行""求人做"。
- 有公开报价与成交案例。

**中信号（B 级证据）**：
- 多人反复求助/抱怨同一问题，但无明确付费记录。
- 用户为"替代方案"付过钱（买工具、外包、请人）。

**弱信号（低价值）**：
- 单纯吐槽、点赞多、播放高。热度 ≠ 付费意愿。

**提问核查**（无公开证据时）：
- 有没有人已经在卖这个？卖多少？
- 用户现在把钱花在哪了？（替代方案/人工/工具）
- 如果免费替代品存在，用户为什么还要付钱？

**付费信号一律要用 Payment Search 复核**（是否有在售服务/价格/成交），不凭单条评论下结论。

## 2. 付费评分分档

见 `references/problem-framework.md` §评分绑定证据（Payment 分档）。要点：

| 分数 | 含义 |
|---|---|
| 1-3 | 几乎没有真实付费证据 |
| 4-6 | 存在类似产品/服务收费，但与当前机会关联一般 |
| 7-8 | 存在明确的类似产品、服务、外包或公开价格 |
| 9 | 存在大量明确付费行为、成熟市场或明显交易证据 |
| 10 | 已经出现针对当前具体方案的真实购买/报价/成交验证 |

**禁止**：因为"用户有痛点"就自动提高 Payment 分数。Payment 只认付费证据。

## 3. 第一笔钱执行清单（Execution Mode）

当用户进入"我要赚钱 / 我要拿第一单 / 我准备做"阶段：
**不要继续生成新的项目清单。** 围绕当前 Opportunity（`opportunity-state-machine.md`）直接执行：

1. **找谁**：第一类最可能付钱的具体用户（写画像）。
2. **去哪里找**：该用户群聚集的真实渠道（群、社区、线下、平台）。
3. **提供什么结果**：一个能立即交付的最小结果（不是产品，是结果）。
4. **怎么展示 Demo**：案例/样例/对比（之前 vs 之后）。
5. **怎么报价**：小额起步（10 / 30 / 50 / 100 元），按"结果价值"定价而非"工时"。
6. **怎么交付**：手工 + AI 完成，明确交付物与期限。
7. **怎么收钱**：先收钱再交付，或先小额定金；允许先小单验证，但不要无限免费。
8. **今天做什么**：给出今天就能执行的 1-3 个动作。
9. **验证成功标准**：明确"到什么结果算成功"（如 1 个付费）。
10. **如果失败下一步怎么办**：预设失败时的调整方向（换人群/换报价/换渠道/放弃）。

**第一笔钱的意义**：验证 `真实问题 → 真实解决方案 → 真实支付` 这条链路通不通，而不是赚多少钱。
**允许低价验证**：10 / 30 / 50 / 100 元都行。重点不是价格高低，而是验证真实支付是否成立。

**购买意愿 ≠ 真实付款（重要）**：
- "愿意购买 / 愿意尝试 / 报价意愿"只是验证信号，最多推进状态机到 `CUSTOMER_FOUND`（已找到明确存在需求的真实潜在客户）。
- `FIRST_PAYMENT`（第一笔钱）**必须实际收到真实付款**（转账、定金、成交款）才能进入。
- 不得因为"用户说愿意付钱"就把状态推进到 FIRST_PAYMENT。报价后收到钱，才算第一笔钱。

## 4. 定价原则

- 价格锚在"用户当前为此付出的成本"（时间×时薪、外包费、返工损失）附近或更低。
- 允许从很小金额开始，逐步提价。
- 不虚构定价依据：报价必须能解释"为什么值这个价"。

## 5. 验证指标（示例，需按项目调整）

典型漏斗（示意）：
```
10 个潜在用户 → 3 个愿意尝试 → 1 个愿意付费
```
按项目自定义：接触数 / 回应数 / 试用数 / 付费数 / 复购数 / 推荐数；单笔金额、月收入目标、交付耗时。

**判定规则**：
- 达标 → 继续并标准化。
- 部分达标 → 调整定位/定价/渠道再试一轮。
- 连续多轮无付费 → 进入"停止机制"。

## 6. 停止机制（Stop Conditions）

出现以下任一情况，**主动建议停止**并输出【不建议继续】：

- 没有真实问题证据。
- 只有单个偶然案例。
- 没有重复需求。
- 没有任何解决方案市场。
- 没有付费行为。
- 用户已有成熟且满意的解决方案。
- AI 无法明显降低成本/时间/技能门槛。
- 竞争强度远超个人能力。
- MVP 无法快速验证。
- 必须投入大量资金/团队/开发周期。
- 用户本人无法触达目标客户。

**停止时必须说明**：
1. 为什么停止（一句话）。
2. 哪个证据导致停止（引用对应证据，说明它证明了什么、不能证明什么）。
3. 未来出现什么新证据可以重新启动（明确触发重启的信号）。

**禁止为了"给用户一个机会"而强行生成方案。** 停在这里也是一种高质量交付。
