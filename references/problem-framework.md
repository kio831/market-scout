# Problem Framework — 问题框架（v1.1）

本文件定义 Problem Card 的字段语义、问题分类、证据等级、**证据绑定评分（含 Payment 分档）**、三池维护与商业嗅觉训练。用于 Problem Analysis / Demand Expansion / 日常观察训练。

## 1. Problem Card 字段定义

每捕获一个候选问题，填 `templates/problem-card.md`。字段语义如下：

| 字段 | 含义 | 必须写什么（不要写什么） |
|---|---|---|
| 问题 | 一句话描述核心痛点 | 写"人工录入核对销售数据太慢且易错"，不写"做个数据工具" |
| 用户 | 谁遇到这个问题 | 写具体画像（如"30-50 人规模餐饮连锁的运营"，可含数量级），不写"所有人" |
| 场景 | 在什么场景/流程中发生 | 写发生位置（每日打烊后、月底对账时…） |
| 频率 | 多久发生一次 | 写可量化估计（每天/每周/每月几次），标注是观察还是估计 |
| 痛苦 | 痛在哪 | 写时间/成本/风险/情绪损失，尽量量化 |
| 当前解决方式 | 现在怎么做的 | 写现状（人工、Excel、外包、免费工具、将就） |
| 为什么不满意 | 现有方式的问题 | 写具体不满（慢、贵、易错、没人手、要学） |
| 潜在损失 | 不解决会怎样 | 写钱/时间/客户流失/合规风险 |
| 付费信号 | 是否有付费迹象 | 写来源："看到有人在问价/已有人收费/用户说过愿意付"；无则写"暂无" |
| AI 可能介入的环节 | AI 能替代/增强哪一步 | 写流程中的具体环节，不写"全程自动化" |
| 需要验证的问题 | 下一步要证实的假设 | 写可检验的疑问（"是否愿意每月付 XX 元？"） |
| 证据等级 | A / B / C | 按 §3 判定 |
| 证据链摘要 | 观察/推断/假设分层 | 按 `evidence-chain.md` 分三段写，不混层 |
| 来源 | 每条证据出处 | 搜索链接 / 评论原文截图 / 现实观察记录；无来源只能到 C |

## 2. 问题十大分类

识别时给问题打一个主标签，便于横向比较与后续扩展：

1. **抱怨型** — 用户明确表达不满（"烦死了""太坑了"）。
2. **重复劳动型** — 同一件事反复做（每天复制粘贴、每周汇总报表）。
3. **时间浪费型** — 大量时间耗在低价值动作（找资料、对数据、沟通确认）。
4. **技能门槛型** — 需要专业能力但用户不会（不会做图、不会剪辑、不会做表、不会写文案）。
5. **信息获取型** — 找不到/难找到需要的信息（比价、找货、找政策、找案例）。
6. **成本型** — 现有方案太贵（人工、外包、工具订阅）。
7. **效率型** — 现有流程慢、吞吐低。
8. **工具复杂型** — 现有软件难用、学习成本高、配置繁琐。
9. **质量/错误型** — 容易出错、质量不稳定、返工（错别字、录错数据、格式乱）。
10. **AI 能力错配型** — 用户想用 AI 但用不对（不会写提示词、不知道能干什么、结果不靠谱）。

## 3. 证据等级

| 等级 | 定义 | 判定要点 |
|---|---|---|
| **A 已验证需求** | 有真实用户证据，并最好存在明确付费行为 | 有可引用的真实来源，且出现付费信号（询价/在售服务/成交）。至少需要"多人反复提到 + 至少一个付费迹象"。 |
| **B 潜在需求** | 有重复需求、抱怨或求助，但缺乏明确付费证据 | 有 2+ 个独立来源提到同类问题/求助；未证实有人为此付钱。 |
| **C 假设需求** | 主要来自模型推测，没有足够真实证据 | 无来源或来源不足；只能作为待验证假设。 |

> **与机会状态名区分**：本节的证据等级 A/B/C **保持不变**，仅用于标注"需求的验证程度"。
> 机会的推进状态**不使用 A/B/C 字母**，统一用完整英文状态名（HYPOTHESIS / DEMAND_CONFIRMED / MARKET_CONFIRMED / PAYMENT_VALIDATION / CUSTOMER_FOUND / FIRST_PAYMENT / REPEATED_DELIVERY / STANDARDIZED / AUTOMATED / PRODUCTIZED，见 `opportunity-state-machine.md`）。两者互不冲突。

**禁止规则**：
- 不得把"推测"写成"发现"；不得因"我认为很多人需要"就把 C 写成 B。
- 证据升级必须有新增真实证据（新来源、新付费迹象）。
- 报告中每条机会必须显式标注当前等级，以及"升到 A 需要补什么证据"。

## 4. 评分绑定证据（P1 强化）

对值得继续的问题逐维打分 1-10。**禁止仅凭主观感觉打分。**

### 8 个维度

| 维度 | 含义 | 高分指向 |
|---|---|---|
| Pain | 痛苦程度 | 不解决有明显损失、情绪强烈 |
| Frequency | 发生频率 | 高频（每天/每周）优于低频（一次性） |
| Payment | 付费证据 | 已有付费行为/在售服务/询价，越高越好 |
| Market | 市场证据 | 搜索到越多真实抱怨/求助/竞争，越高 |
| AI Leverage | AI 杠杆 | AI 比人工能显著降本/提速/提质 |
| Feasibility | 个人可执行性 | 个人（或小团队）能完成交付，不需要重资源 |
| MVP Speed | MVP 速度 | 能在一周内做出最小交付物 |
| Competition | 竞争难度 | **分数越低越好**（越低 = 越少/越弱的竞争） |

### 每个分数必须给出四要素

```
分数：N/10
评分理由：为什么给这个分（一两句）
对应证据：引用 Evidence Card 中的证据 / 明确写【无直接证据，基于推断/假设】
当前不确定性：这个分最可能被推翻的地方
```

### Payment 分档（硬性参考，禁止"有痛点就给高分"）

| 分数 | 含义 |
|---|---|
| 1-3 | 几乎没有真实付费证据 |
| 4-6 | 存在类似产品/服务收费，但与当前机会关联一般 |
| 7-8 | 存在明确的类似产品、服务、外包或公开价格 |
| 9 | 存在大量明确付费行为、成熟市场或明显交易证据 |
| 10 | 已经出现针对当前具体方案的真实购买/报价/成交验证 |

**注意**：不要因为"用户有痛点"就自动提高 Payment 分数。Payment 只认付费证据。

### Competition 分档（越低越好）

| 分数 | 含义 |
|---|---|
| 1-3 | 竞争很激烈/巨头/免费替代强 |
| 4-6 | 有竞争者但存在明显缺口 |
| 7-8 | 竞争少，个人有明确切入空间 |
| 9-10 | 几乎无人做，个人可低成本切入 |

### 使用方法
- 总分用于粗排，**不能只看总分下结论**。
- 每个候选必须写出四问：为什么值得继续？最大的不确定性是什么？缺什么证据？下一步最应该验证什么（只做一件事）？
- Competition 与其它维度方向相反，比较时单独列。

## 5. 三池维护

长期运行中维护三个逻辑池，每次侦察结果都归入对应池：

- **Result Pool（结果池）**：AI 当前能帮人完成什么结果。例：生成商品图、写周报、整理发票、做 PPT、审合同、做小红书封面。
- **Demand Pool（需求池）**：谁需要什么结果。记录"用户画像 × 想要的结果"。
- **Payment Pool（付费池）**：谁已经在为类似结果付钱。记录"在哪付/付给谁/付多少"。

**优先级**：优先研究 `问题 + 已存在解决方案 + 已存在付费行为` 三者同时成立的机会（需求被证实、竞争可拆解、定价有锚）。

**Demand Expansion（寻找类似需求）**：
1. 从已知问题出发，问"同样的用户还有哪些别的麻烦？"（横向扩痛点）。
2. 问"还有哪些用户有同样的问题？"（纵向扩用户群）。
3. 问"类似结果，谁在付钱？"（扩付费池）。
4. 只保留有来源支撑的新问题，其余标 C 待验证。

## 6. 商业嗅觉训练（日常观察）

把看到的信号自动转成问题假设：

| 你听到/看到 | 问题信号 |
|---|---|
| "这个好麻烦" | 是否存在问题？ |
| "有没有工具" | 是否存在需求？ |
| "多少钱" | 是否存在付费信号？ |
| "每天都要做" | 是否存在重复劳动？ |
| "我不会" | 是否存在技能门槛？ |
| "这个软件太复杂" | 是否存在简化机会？ |
| "太贵了" | 是否存在成本型机会？ |
| "老是出错/又返工" | 是否存在质量/错误型机会？ |

训练目标：从"看内容的人"变成"观察需求的人"。观察到的每一条都先记 Problem Card（可标 C），再通过三类搜索验证升级。
