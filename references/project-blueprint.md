# Project Blueprint — 机会转项目（v2.0 新增，流水线第 4 阶段 BLUEPRINT）

本文件定义把一个已通过评估（EVALUATE 结论为 🟢 或"验证后可转 🟢 的 🟡"）的机会，转化为**可执行项目方案**的方法：推荐产品形态、核心用户、核心功能、MVP 范围、推荐技术方向、最小验证方案、差异化切入点。产出为 `templates/project-blueprint-card.md`。

> 阶段定位：FIND → VALIDATE → EVALUATE → 【BLUEPRINT（本文件）】→ MONETIZE。
> 本阶段是 v1.1 `ai-solution-patterns.md`（Level 1-5、可落地方案清单、MVP 原则、降级规则）在 V2 流水线中的结构化延伸，**优先复用，不重复定义**。

## 0. 进入条件与输入

进入本阶段必须已有：
- VALIDATE 产出：需求强度、核心用户、付费理由链（`demand-validation.md`）。
- EVALUATE 产出：综合结论、AI 可实现度、差异化切入点、风险（`project-evaluation.md`）。

缺任一输入，退回上一阶段补齐，禁止凭空白直接"设计产品"。🔴 NO-GO 的机会不进入本阶段。

## 1. 推荐产品形态（Product Form，对齐 Level 1-5）

复用 `ai-solution-patterns.md` §1 的 Level 1-5，**按当前证据选择"现在该停在哪一级"，而不是选"最终想做哪一级"**：

| 形态 | 对应 Level | 何时推荐（证据条件） |
|---|---|---|
| 人工+AI 代做/咨询（Concierge） | L1 | 尚无付费用户；需要最快验证"结果是否有人付钱"（默认起点） |
| 半自动化服务 | L2 | 已有 1-3 个付费用户、交付流程已跑通 |
| 自动化工作流 | L3 | 交付重复稳定、人工只需质检 |
| 单功能小工具 | L4 | 高频重复任务已被付费验证、用户想自助 |
| SaaS/完整产品 | L5 | 有规模与留存证据后 |

输出必须写明三件事：
1. **现在推荐形态**（默认从 L1 起，除非已有证据支持更高级）。
2. **为什么是它**（引用 EVALUATE 的 AI 可实现度/开发难度证据）。
3. **升级到下一级的触发证据**（如"5 个付费客户 × 重复交付 2 次"才允许 L2→L3）。

没有真实付费用户前，禁止默认推荐 L4/L5（沿用 v1.1 铁律：先卖结果，再产品化）。

## 2. 核心用户（Core User，收窄到可触达的一群人）

直接继承 VALIDATE 的"核心用户"并进一步收窄为**首个版本只服务的人群**：
- 一句话用户画像（身份 + 场景 + 最想要的结果）。
- 他们在哪里聚集（具体渠道/社群/线下场景，传给 MONETIZE）。
- 明确"第一版不服务谁"（防止功能与人群蔓延）。

## 3. 核心功能（Core Features，MoSCoW 优先级）

围绕"用户要的结果"反推功能，分四档：

| 档位 | 含义 | 取舍规则 |
|---|---|---|
| **M Must-have** | 没有就无法交付那个结果 | 第一版只保留 M，且 M 通常 ≤ 3 项 |
| S Should-have | 重要但可人工替代/延后 | 第一版用人工顶，不写进 MVP |
| C Could-have | 锦上添花 | 不做 |
| W Won't-have（now） | 明确本期不做 | 显式列出，防止蔓延 |

每个 M 功能必须回答：它服务于哪个付费理由（VALIDATE §5）？去掉它用户还会付钱吗？不会付钱的功能一律降级。**禁止把"AI 能做"等同于"用户要"。**

## 4. MVP 范围（复用 v1.1 MVP 原则，五项必填）

严格沿用 `ai-solution-patterns.md` §4，五项一个都不能少：

- **【第一版做什么】**：只交付核心结果所需的最小集合（Must-have + 推荐形态）。
- **【第一版不做什么】**：显式列黑名单（不做账号体系/不做后台/不做 App/不做自动化同步……按项目写）。
- **【验证什么】**：第一优先验证"是否有人为结果付钱"，其次才是留存/效率。
- **【什么结果出现后继续（继续条件）】**：可量化（如 2 周内 ≥3 人付费、≥1 人复购）。
- **【什么结果出现后放弃/转向（停止条件）】**：可量化（如接触 20 人无人愿付、或都要求先做一堆 S/C 功能才考虑）。

同时给出：预计现金成本、时间成本（到第一次可交付）、交付方式。

## 5. 推荐技术方向（Tech Direction，生产级要求沿用 v1.1）

只在选定形态需要技术时填写，沿用 `ai-solution-patterns.md` §3 的生产级要求（异常处理、输入校验、日志、超时重试、配置管理、安全），并回答：
- **技术选型**：无代码组合 / 轻脚本（Python+SDK）/ 简单前端 / 完整产品——与 Level 对应，优先依赖最少的方案。
- **AI 做什么 / 人做什么**：划清自动化边界与人工质检点。
- **选型理由 + 最大缺点 + 替代方案**。
- **第三方依赖与成本**：模型/API/数据源，单项依赖失败时的兜底（对接 `pipeline-and-runtime.md` 的降级规范）。
- **数据结构预留**：核心交付物的数据结构要稳定、字段清晰（为后续 L2→L5 自动化与 MONETIZE 模块独立化留接口，见 `monetization-gtm.md` §8）。
- 若当前形态为 L1 且无需写代码，明确写【当前不需要开发】——这是合格结论，不是缺项。

## 6. 最小验证方案（Smallest Test of Value）

在"开发之前/同时"，用最小成本验证最致命假设。每个实验写清 5 要素：

```
验证假设：一句话（来自 EVALUATE 的最弱项/最大不确定性，优先验证付费）
实验形式：Concierge 代做 / 冒烟测试落地页 / 预售 / 众筹 / Fake Door / 用户访谈 / 样品试交付（对接 monetization-gtm.md §7）
目标对象：几个、什么画像、从哪来
成功标准：量化阈值（几人愿意付/收多少定金/什么反应算通过）
失败转向：不达标时换人群/换报价/换形态/放弃的具体规则
```

最小验证方案与 MVP 的关系：**验证方案回答"要不要做"，MVP 回答"第一版做成什么样"**；能用不开发的验证方式拿到付费证据的，先拿钱再开发。

## 7. 差异化切入点（Wedge，继承并落地）

继承 EVALUATE §3.2 选出的主切入点，把它落成**产品/交付层面的具体做法**：
- 一句话差异化主张（对谁、在哪个场景、比现有方案好在哪、凭什么是你）。
- 对手要复制需要付出什么成本（时间/资源/基因冲突）。
- 这个差异在 MVP 里通过哪个功能/服务体现（必须落到具体交付物，不能停在口号）。

## 8. 输出要求（Project Blueprint Card）

- 使用 `templates/project-blueprint-card.md`：推荐形态（含升级触发证据）、核心用户、MoSCoW 功能表、MVP 五项、技术方向、最小验证方案、差异化落地。
- 输出一张"项目一页纸"摘要：**卖给谁 → 交付什么结果 → 第一版长什么样 → 怎么验证付费 → 凭什么是你**。
- 本阶段产出（Offer 雏形、交付形态、成本结构、核心用户渠道）是 MONETIZE 阶段的直接输入，数据契约见 `pipeline-and-runtime.md`。
