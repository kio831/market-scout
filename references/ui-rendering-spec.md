# UI Rendering Spec — 输出渲染与视觉规范（v2.0.0 新增，文档型 Skill 的 Design System）

> Market Scout 是纯 Markdown 文档型 Agent Skill，没有独立前端。**"界面"就是 Agent 输出的 Markdown 报告与卡片**。
> 本文件定义统一的输出渲染规范，让所有阶段卡、报告、状态提示在任何支持 Markdown 的客户端（桌面/移动）上都呈现专业、一致、可读的视觉。
> 所有 v2 模板（`templates/*-card.md`、`opportunity-report.md`）与运行时输出必须遵守本规范；运行时健壮性（超时/降级）见 `pipeline-and-runtime.md` §3。

## 1. 设计原则

1. **结论先行（Conclusion First）**：用户 10 秒内必须看到"在分析什么 → 得到了什么 → 下一步做什么"。
2. **信号一致（Consistent Signals）**：同一含义永远用同一视觉符号（信号灯、分数条、状态标签），不随意换。
3. **证据可溯（Traceable）**：每个分数/结论旁可一眼看到证据或【无直接证据】标注。
4. **克制不堆砌（Restrained）**：不用大段 emoji、不用花哨配色，信息密度优先于装饰。
5. **移动优先（Mobile-first）**：先保证手机竖屏可读，再利用桌面宽屏做对比表。

## 2. 字体与标题层级（Typography）

| 层级 | 用法 | 示例 |
|---|---|---|
| `# H1` | 每份报告/卡片唯一主标题，含产品名与阶段 | `# Opportunity Report 机会报告` |
| `## H2` | 大段落（阶段、模块） | `## 3. EVALUATE 项目评估` |
| `### H3` | 子模块/小节 | `### 七维评分` |
| `#### H4` | 字段组标题（尽量少用） | `#### 付费理由链` |
| 正文 | 15-25 字一行感，关键术语加粗 | `**需求强度**：7.0/10` |
| 行内代码 | 字段名、状态代码、ID、路径 | `MS-101`、`GO`、`Demand Strength` |

- 一份报告 H1 只出现一次；H2 不超过 12 个，超长报告用目录锚点。
- 关键数字、结论、行动动词用 `**加粗**`；不要整段加粗。

## 3. 间距与分隔（Spacing & Dividers）

- 段落之间空一行；H2/H3 上方空两行，营造呼吸感。
- 大阶段之间用 `---` 水平分隔线；卡片内部小字段用表格或"字段：内容"，不用分隔线。
- 列表项之间不空行；嵌套列表缩进 2 空格。

## 4. 卡片与容器（Cards & Containers）

Markdown 无原生卡片，用以下结构模拟：

### 4.1 结论带（Verdict Banner，每份输出顶部必有）
```
> **🟢 值得做 GO**　|　综合机会评分 **74/100**　|　需求强度 **7.0/10**　|　Opportunity **MS-101**
> 一句话结论：本地小型教培工作室获客内容代做，需求真实但付费未验证，建议先做两周最小实验。
```
- 引用块 `>` 模拟 Banner；信号灯 + 核心数据 + ID 一行；第二行一句话结论。
- 三档结论固定：🟢 `GO` / 🟡 `VALIDATE_FIRST` / 🔴 `NO_GO`（中文+英文代码双语）。

### 4.2 阶段进度条（Pipeline Progress，五阶段输出必有）
```
`FIND ✅ → VALIDATE ✅ → EVALUATE ✅ → BLUEPRINT 🔄 → MONETIZE ⏳`
```
- 状态符号：`✅` 已完成 / `🔄` 进行中 / `⏳` 待开始 / `⚠️` 有降级或证据不足。
- 让用户一眼看到"AI 正在分析什么、进行到哪一步"。

### 4.3 数据卡（Metric Card，关键指标）
用三列表格承载 3-6 个关键指标，桌面横向、移动端自动换行：
| 指标 | 值 | 依据 |
|---|---|---|
| 需求强度 | 7.0/10 | 6 信号均分 |
| 综合评分 | 74/100 | 7 维加权 |
| 建议形态 | L1 人工+AI | AI 可实现度 8 |

### 4.4 证据卡（Evidence Card，沿用 v1.1）
每条重要证据独立成块，7 项属性齐全（`templates/evidence-card.md`）。

## 5. 评分可视化（Scoring）

### 5.1 分数条（统一 10 格，禁止换样式）
```
需求强度     ███████░░░ 7/10
市场潜力     ██████░░░░ 6/10
AI 可实现度  ████████░░ 8/10
```
- `█` 实心 = 得分，`░` 空心 = 剩余；维度名左对齐占固定宽度，分数右对齐。
- 0-10 分；加权综合分用 0-100 数字 + 百分条（20 格，每格 5 分）。

### 5.2 评分表（每分必带四要素）
| 维度 | 分 | 理由 | 证据 /【无直接证据】 | 不确定性 |
|---|---|---|---|---|
- 桌面用此表；移动端（窄屏）改为纵向"维度：分 — 理由（证据）"键值列表，保证不横向溢出。

### 5.3 计算式（可复算）
综合分必须附计算式，用 ```text``` 代码块：
```text
Score = (7×.20 + 7×.20 + 6×.15 + 8×.15 + 9×.10 + 8×.15 + 7×.05) × 10 = 74/100
```

## 6. 行动按钮与下一步（Actions）

行动建议用统一格式，模拟按钮：
```
**👉 下一步（只做一件事）**：给 3 家小店免费做 1 条样品并报价 199 元首月。
[📋 执行清单](references/payment-validation.md#第一笔钱)　[🔬 最小实验](templates/project-blueprint-card.md)
```
- 行动动词开头（给/做/找/发/约），可量化、今天能做。
- 相关模板/方法用 Markdown 链接，标注 emoji 类型（📋清单/🔬实验/📊报告/⚠️风险）。
- 禁止"继续研究""深入分析"这类无动作的建议。

## 7. 四种状态（Loading / Empty / Error / Success）

所有运行时输出必须明确标注当前状态，让用户知道"AI 正在做什么/出了什么问题"。

### 7.1 Loading（分析进行中）
```
`🔄 正在分析：EVALUATE 项目评估`
正在执行：7 维加权评分计算（需求强度继承自 VALIDATE=7.0）…
预计：本阶段约需 3 次外部检索 + 1 次评分合成。
```
- 标注当前阶段、正在做的具体动作、预计步骤；不假装已完成。

### 7.2 Empty（无证据/空结果）
```
`⚠️ 空结果 EMPTY`
Payment Search 未找到公开付费证据。
→ 处理：该维度标【证据不足】，Payment 评分上限 4，结论不得判为强商业机会。
→ 建议补证据：搜"XX 代做 价格/报价"或直接访谈 3 位目标用户。
```
- 明确说"没找到什么"、"因此怎么降级处理"、"去哪补"；禁止用模型记忆补成"事实"。

### 7.3 Error（调用失败/降级）
```
`❌ 调用失败 ERROR（已降级）`
通用搜索超时（>20s，重试 2 次后仍失败）。
→ 降级路径：改用用户提供材料 + 已采集证据；本阶段结论标【假设分析，未实时验证】。
→ 影响：综合分可信度降为中，建议用户联网后重跑 EVALUATE。
```
- 写明失败原因、已执行的重试/降级、对结论的影响、恢复方式；不静默失败。

### 7.4 Success（验证通过/阶段完成）
```
`✅ 阶段完成 SUCCESS：VALIDATE`
需求强度 7.0/10（中等偏强），需求结论：需求存在但付费未验证。
→ 进入下一阶段：EVALUATE（继承需求强度=7.0，不重打）。
```
- 给出本阶段关键产出 + 明确下一步；阶段产出落卡（结构化字段齐全），支持断点续跑。

## 8. 长报告阅读体验（Long Report）

- 顶部必有**目录**（锚点链接到各 H2），长报告（>5 屏）必须有。
- 每阶段开头重复一次**阶段进度条**（§4.2），让用户随时知道位置。
- 关键结论在每阶段末尾用 `> **本阶段结论**：…` 引用块小结。
- 报告末尾必有**行动路线**（今天/本周/2-4 周）+ **最终判定**。
- 证据原文长引用用 `>` 引用块，不超过 3 行；超长证据折叠为"见 Evidence Card E-00X"。

## 9. 移动端优先（Mobile-first）

- 任何表格列数 ≤ 6；超过则拆成多个小表或改纵向键值列表。
- 宽表（>4 列）在输出时附一句"窄屏查看：以下为纵向版"，并给出 `字段：内容` 列表。
- 分数条、进度条用纯文本字符，不依赖图片，任何客户端都能渲染。
- 一行不超过 ~40 个中文字符的信息密度；长句拆短句。
- 按钮/链接单独成行，不挤在段落里。

## 10. 桌面端信息密度（Desktop）

- 桌面端优先用对比表（多列）、并排指标卡，充分利用宽屏。
- 可在报告中用"左：证据 / 右：推断"双栏感（用两列表格模拟）。
- 综合评分、风险矩阵等可用多列表格一次呈现，不用拆段。

## 11. 双语规范（Bilingual）

- 标题/固定标签：`中文（English）`，如 `需求验证（Demand Validation）`。
- 状态代码、字段名、ID：纯英文（`GO`、`Demand Strength`、`MS-101`）。
- 正文：中文为主，关键术语首次出现括注英文，不逐句翻译。
- 三档结论固定双语：🟢 值得做 GO / 🟡 建议验证后再做 VALIDATE_FIRST / 🔴 不建议做 NO_GO。

## 12. 代码与数据结构区（Code Blocks）

- Schema、契约、计算式、配置一律用围栏代码块并标注语言：```yaml / ```json / ```text / ```python。
- 字段名英文、注释中文、缩进 2 空格、字段对齐。
- 代码块前后空一行；行内短字段用反引号。

## 13. 自检清单（输出前必过）

每份 v2 输出交付前逐项核对：
- [ ] 顶部有结论带（信号灯+核心分+ID+一句话结论）。
- [ ] 有阶段进度条，用户知道进行到哪一步。
- [ ] 评分用统一 10 格分数条，综合分附可复算计算式。
- [ ] 每分有证据或【无直接证据】标注，无"市场很大"式空话。
- [ ] 有明确的"下一步只做一件事"行动建议（动词开头、可量化）。
- [ ] Loading/Empty/Error/Success 状态有标注，无静默失败。
- [ ] 表格 ≤6 列，窄屏有纵向版或键值列表。
- [ ] 长报告有目录、每阶段小结、末尾行动路线。
- [ ] 双语规范一致，代码块标注语言。
